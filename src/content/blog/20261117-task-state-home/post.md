> 我们先塑造建筑，之后建筑塑造我们。
> ——温斯顿·丘吉尔

群里有人聊起任务状态放哪。一种说法是，任务状态不该跟着 session 走，任务会交接、会恢复、会换执行者，session 一关状态就没了。有人问，那是不是 sessionless。有人说，按 PR 走。马上有人反对：PR 只能用于代码，并发开发起来也不行，rebase 到天荒地老，stacked PR 一样救不了。

这里前两句都对，最后一句的方案错了。任务状态确实不能住在 session 里，但它也住不进 PR。这篇想把「住不进」拆开讲清楚，顺便讲讲它该住哪。

## 一、git 早就回答过一次这个问题

先看一个已经解掉的类似问题：「一段代码写到哪了」。

没有版本控制的时候，这个状态活在编辑器里。哪些文件改了、改到哪一行，都在缓冲区里，编辑器一崩全没了。git 出来之后这个问题消失了。commit 是一份不可变的快照，branch 只是一个可以移动的指针，工作到哪，指针指到哪。换台机器，clone 一下，接着干。

状态没有跟着任何一个工具走。编辑器可以关，终端可以崩，仓库还在。

git 还留了一样东西，reflog。谁、在什么时候、把哪个指针从哪挪到了哪，一行一条，只追加，不覆盖。这个形状后面还会反复见到。

代码的状态问题就是这样解的：把状态从工具里搬出来，放进一个独立于所有会话的存储。任务状态面对的是同一道题，只是还没有一个公认的 git。

## 二、PR 的形状装不下任务的形状

一个 PR 能成立，靠三件事同时成立：有一段代码，有一条分支，有一个合并动作。这三件事都有形状，代码有 diff，分支有父子，合并有先后。PR 的界面、评审、回滚，全部长在这个形状上。

任务不是这个形状。「把导入后的搜索问题查清楚」，没有 diff。它可能做完了但没有产出代码，也可能改了三行、结论是「不用改」。它的状态是「在查」「查到了原因」「等人确认能不能动」，塞不进「+12 −3」。

再往下拆一层，问题更清楚。任务的依赖是图，PR 的结构是树。树的定义是每个节点只有一个父亲，stacked PR 就是标准的树，它默认你事先知道改动的先后依赖。任务之间呢，A 等 B 的结论，C 和 D 互不相干但抢同一个人的注意力，一个方案可能被两条不同的讨论各自推翻再拼回来。树装不下这些，硬装，最后维护的就是那棵树本身。「rebase 到天荒地老」说的就是这个代价。

那段讨论里有一条像是笔记摘录的话，把方向指对了：

> 所有链接都是双向且有类型的：PR ↔ thread ↔ artifact ↔ 决定 ↔ session。PR 是结果，thread 是过程。

PR 是结果，一次合并的产物，可回滚、可比较、可引用。thread 是过程，讨论、试错、被否掉的方案、为什么最后没那么做。只有结果，过程就丢了，三个月后看到一个 PR，知道改了什么，不知道为什么这么改。只有过程，结论就找不到，翻完几百条消息，还是不知道最后定了什么。

artifact、决定、session 也都是节点。一个决定是在哪次讨论里做的、由谁执行、产物在哪，这些问题的答案本身就是边。有类型的意思是，边上写着「产生于」还是「推翻于」，机器认得出。

## 三、以前是最佳实践，现在是生存条件

状态外置不是新主张。工单系统、issue tracker 存在几十年了。Jira 的 workflow 就是一台可配置的状态机，状态之间定义转移；Linear 给每个 issue 一个 state，放进 project 和 cycle 里排。这些老发明早就把「任务状态活在会话外面」做成了默认值。

在人类团队里，装了这些系统效率会高，不装也死不了。人有脑子。忘了，走廊里问一句「这事到哪了」就行。人脑是一块跨会话的存储，不可靠，但足够便宜。

agent 没有这块存储。每次会话从零开始，它只读得到写下来的东西。聊天记录算是写下来了，但它是写给当时在场的人的。下一次要接手的人从里面找不到当前状态的指针，只能从头读几百条，读完还未必知道最后定了什么。

会话不幂等，文件幂等。从聊天记录里恢复状态，每次都要整段重读，读出来的还可能不是同一个状态；从外部存储里读状态，读一次就对。前者的成本随历史长度线性涨，后者是个常数。

所以在 agent 时代，外部任务系统从最佳实践变成了前置条件。人可以迁就烂载体，agent 迁就不了，它没有「顺便想起来」这个功能。写下来，它就能接上。

## 四、每一层有自己的原语

群主后来把这件事放进一个更大的框架，三层：

| 层 | 谁和谁在协作 |
| --- | --- |
| agent / product harness | 用户 × agent 产品 |
| repo harness | 多人 × 多 agent × 同一个仓库 |
| org harness | 多人 × 多 agent × 多项目 × 组织内交流平台（Slack、飞书等） |

他写了篇长文讲这个，[《Agent Harness 的三种协作尺度》](https://www.joyehuang.me/blog/20260912---codexharnessevolution/post)。三种尺度不是一层包一层，也不要求按顺序走，同一件事常常同时落在好几层上：做一个内部工具，找人是组织级的，实现是 repo 级的，来回改原型又是产品级的。「万物皆 harness」说的是，只要有人和 agent 一起把事做完，中间让协作进行得下去的那套机制就是 harness。仓库里一条「不要直接 push 到 main」的约定是它，IM 里替你翻旧讨论、告诉你该去找谁的 agent 也是它。

他那篇里有一条推理值得单独记：模型变强，减少的是教它完成某一步的机制，增加的是让彼此协作的机制。测试提醒、Todo 这类补丁，模型学会了就可以拆；权限、状态、交接、反馈，是协作本身的长期需求，交出去的工作越多，它们越重。Bun 从 Zig 重写到 Rust 是现成的例子，一个 prompt 加一个调度大量 agent 的工作流，64 个实例并行，跑了 11 天，2026 年 5 月合入 main。能成，靠的不是提示词，是 Bun 和 Node.js 本来就有一大套测试，结果对不对随时可以验证。

PR 是 repo 层的原语。组织层的状态既不属于某个仓库，也不属于某次会话，拿它去同步组织层的事，等于拿代码的坐标系去描述组织的形状。科日布斯基有句话说的就是这件事：「地图不是疆域本身。」每层有自己的疆域，就得有自己的地图。

## 五、载体的三条设计

前面四节收拢成一句话：任务状态要有自己的家，不挂在 session 上，不塞进 PR。落到设计上是三条。

第一条，状态外置。存储形态不重要，外部任务系统、一张表、一个文件都行，标准只有一条：会话关掉之后还读得到。状态长在任务上，不长在对话上。「在查」「查到原因」「等人确认」，每变一次写一次，谁改的、什么时候改的，跟着记录走。接手的人打开任务，看到的是当前状态，不是几百条聊天记录。

第二条，决定要有来路。一个方案什么时候定的、当时为什么这么定、后来为什么改，要能顺着链接走回去。PR 连 thread，thread 连决定，决定连 session，边上有类型。没有这些链接，三个月后看到一个合并，知道改了什么，不知道为什么；更常见的是没人知道为什么，于是再讨论一遍、再定一遍。桑塔亚纳说，记不住过去的人，注定要重蹈覆辙。系统记不住，也一样。

第三条，只追加，不覆盖。谁在什么时候把状态从 A 改成 B，一行一条，事后能整段回放。这个形状在三个不相干的地方都出现过：git 的 reflog，数据库的 write-ahead log，事件溯源里的 event log。数据库先写日志再改数据，写坏了也能回放；事件溯源干脆把「当前状态」定义成事件的折叠，想要任何时刻的状态，就把事件回放到那为止。任务状态值得同样的待遇，因为回放回答的不只是「现在是什么」，还有「怎么走到这一步的」。

这三条没有一条是新发明，新的只是读者里多了 agent。人读载体，扫一眼重点就行；agent 读载体，靠的是写得明明白白的链接和类型。写下来的东西，人和 agent 都能接上。

结果合进 main 就有了家，过程还睡在聊天记录里。

回到开头那场群聊。「按 PR 走」这个方案错了，但它指着的问题是真的，状态在 session 里留不住，在 PR 里塞不下，需要一个会话关掉之后还在的家。丘吉尔那句话到这里可以再读一遍，我们先塑造建筑，之后建筑塑造我们。载体就是这样的建筑，先是我们挑它，后来是它反过来规定我们，哪些事接得上，哪些事一关会话就断了。挑载体的时候多想一步，任务、讨论、决定各有各的家，往后人和 agent 一起做事的样子，就是这一步长出来的。
