整理自学习笔记《解决窗口太长，AI 漂移问题》。这里记录一种协作方法，不把换窗口当成保证模型正确的办法。

## 换窗口容易，接着做才难

一段对话里可能先讨论需求，后来改方案，再修错误，最后开始验收。如果只把整段对话搬过去，新窗口还需要重新判断：哪些是最终决定，哪些想法已经放弃，哪些工作真正完成了。

所以交接时，我更关心“现在处于什么状态”。一句“页面已经修好”不够，还要知道修改在哪个文件、验证过什么、哪些部分没有检查。

## 交接内容要让下一步能开始

我想保留六类信息：

| 内容           | 应该回答的问题                           |
| -------------- | ---------------------------------------- |
| 当前目标       | 最终要得到什么，本轮只完成其中哪一部分？ |
| 关键约束       | 哪些决定已确认，哪些操作还没有授权？     |
| 当前文件与版本 | 从哪里继续，工作区有没有未提交修改？     |
| 已完成与验证   | 改了什么，用什么方法确认，结果是什么？   |
| 未解决的问题   | 还有哪些失败、不确定或依赖？             |
| 下一步与验收   | 接下来先做哪件事，什么结果算完成？       |

不是每次都要写满一大页。改一句文案只需要很短的说明；跨文件修改、调试到一半的任务，才需要更多上下文。

## 一个可改写的交接模板

下面是模板，里面的括号需要替换为实际事实，不是对某个项目状态的声明。

```text
目标：[用户最终想得到什么]
当前任务：[这一轮要完成的具体事项]
已确认约束：[保留的行为、范围、授权边界]

工作位置：[仓库、分支、相关文件]
已有修改：[已完成的修改；是否提交]
验证记录：[实际执行的检查、结果、未覆盖部分]

当前问题：[观察到的现象、复现条件、已有证据]
已排除方案：[尝试过什么，为什么没有继续]
下一步：[首先执行的一项具体动作]
完成标准：[用户能观察到的结果]
```

“准备运行测试”和“测试已经通过”不能合并成一句。计划也不能写成已完成。新窗口如果无法访问文件或旧会话，就需要补充实际内容；只给一个会话编号，并不意味着它一定读得到。

## 接手后先核对会变化的事实

交接稿只是一个时间点的记录。期间可能有人又改了代码，服务也可能停止。因此接手后应该先确认当前分支、修改状态、相关文件和必要的运行结果。

例如交接写着“剩下移动端检查”，下一步就应该打开移动端尺寸复现，而不是重新设计整个页面。若当前文件与交接不一致，先找出差异，再决定接着哪里做。

## 什么时候值得交接

我会优先考虑两个时机：一个阶段结束，准备切换任务；或者对话开始反复遗漏约束、重复已经排除的方案。

但回复慢也可能来自网络、工具等待或服务负载。不能仅凭卡顿就判断上下文太长，更不能保证新开窗口一定解决问题。先看实际症状，必要时再整理状态。

目前我想养成的习惯是：在关键决定和验证结果出现时，及时留下短记录，而不是等到整个对话已经混乱了才要求一次完美总结。

## 还需要继续观察

交接稿多短才够用？哪些遗漏最容易让后续工作重做？我准备从下一次真实交接里记录“新窗口首先追问了什么”，用这些缺口改模板，而不是不断增加固定栏目。
