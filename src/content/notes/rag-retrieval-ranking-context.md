整理自学习笔记《RAG》。这次先把检索链路理顺，实验数字等回到原始评测记录核对后再补。

## 答案错了，不一定该先换模型

RAG（检索增强生成）先找资料，再让模型依据资料回答。最终答案不对，可能是资料没找到，也可能是找到了却没送到模型面前，还可能是模型拿到了证据却理解错了。

我现在会先沿着这条链检查：

```text
原始文档 → 切块与索引 → 候选召回 → 排序 → 上下文选择 → 生成回答
```

切块在建索引时就发生了。把“召回、排序、切块、上下文”记成优化清单可以，但不能误认为这就是运行顺序。

假设问题是“函数超时后会重试几次”，答案在文档中的一个段落里：

| 观察到的现象                   | 先检查什么                       |
| ------------------------------ | -------------------------------- |
| 候选列表完全没有那个段落       | 索引是否完整、查询表达、召回策略 |
| 段落在第 18 位，只取前 5 条    | 排序与候选截断位置               |
| 段落排进前 5，却被上下文筛掉   | 筛选规则、去重与长度预算         |
| 数字留下了，适用条件被切走     | 切块边界、标题与相邻段落         |
| 完整证据已经送入，答案仍然编造 | 提示词、引用约束与生成结果       |

这是一个排查用的假设例子，不是项目测量结果。它提醒我：只看最终答案，无法判断应该改哪一层。

## 混合检索补的是不同类型的漏召回

BM25（关键词检索）依赖词项匹配，函数名、错误码这类精确表达适合先看这一路。Dense Retrieval（稠密向量检索）根据向量相似度找候选，能补充一些用词不同但含义接近的表达。

把两路放在一起，重点在于它们是否找到了互补的资料。不能默认“多加一路就一定更好”：分词方式、语料内容、候选数量都会影响结果。

[RRF（倒数排名融合）](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)是合并结果的一种办法。它利用各路排名，而不是直接把量纲不同的原始分数相加。排得靠前、同时出现在多路结果里的文档，往往更容易获得较高融合分数。但融合仍然需要去重，也不能凭空找回两路都漏掉的证据。

## 重排序只能重排已有候选

Cross-Encoder（交叉编码器）把问题和候选文本一起输入模型，给它们的相关性打分。因为需要逐对处理，通常先用检索缩小范围，再对有限候选重排；这是[检索与重排序文档](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)介绍的两阶段做法。

我的理解是：它适合尝试解决“证据找到了，但排在后面”。如果证据根本没有进入候选池，换再强的重排模型也不能修复这次漏召回。

另一个容易混淆的地方是，相关性分数并不等于事实正确的概率。一段高度匹配问题的旧文档，也可能已经过时。

## 给模型的上下文需要够用，也需要完整

切块太短，条件和结论可能分离；切块太长，又可能把大量无关内容带进来。按标题和段落切分有助于保留结构，但也要处理长章节、表格、重复标题，不能把“结构化”当作效果保证。

上下文选择位于候选之后。这里可以去重、限制总长度、保留必要邻接内容。但筛得更短不等于筛得更好：删掉条件句，留下一个数字，反而会让回答更自信地出错。

## 下次实验要留什么

我想先保留一个简单基线，再一次改一处。每道问题至少记录：标准证据、召回候选、排序位置、最终上下文和答案。

- **召回层**：目标证据有没有进入候选？
- **排序层**：它是不是排到了实际会采用的位置？
- **上下文层**：证据是否完整，混入了多少无关内容？
- **回答层**：结论是否有依据，引用能不能支持对应的句子？
- **代价**：增加了多少等待时间和模型调用？

还要继续验证的问题是：重排序的收益在哪类问题上最明显？上下文删减到什么程度会开始丢条件？下一次比起只写“效果提升”，更值得留下的是具体失败样本和它在哪一步得到改善。
